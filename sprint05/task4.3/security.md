# Базовые меры безопасности

## Аутентификация

Мобильное приложение использует OAuth 2.1 / OpenID Connect Authorization Code
Flow with PKCE. Mobile API Gateway выполняет роль Authorization Server:
аутентифицирует пользователя, поддерживает MFA для рискованных входов, выпускает
короткоживущий JWT access token на 5 минут и rotating refresh token на 30 дней.
Авторизация открывается через системный браузер; приложение не хранит пароль
пользователя и не имеет client secret.

Access token передаётся только в заголовке
`Authorization: Bearer <access_token>` по TLS. Refresh token хранится в iOS
Keychain или Android Keystore и передаётся только в token endpoint Gateway.
Перед маршрутизацией Gateway проверяет подпись, `iss`, `aud`, `exp`, scopes и
статус сессии. Запрос и исходный токен передаются в Mobile BFF по mTLS, где токен
проверяется повторно, а `patientId` берётся из `sub`. Внешние служебные заголовки
Gateway предварительно удаляет, поэтому приложение не может подменить доверенный
контекст или запросить карточку другого пациента.

## Rate Limiting

| Тип запроса | Лимит | Действие при превышении |
| --- | --- | --- |
| Публичный поиск врачей `GET /api/v1/doctors` | 60 запросов в минуту на IP, burst не более 10 запросов в секунду | Вернуть `429 Too Many Requests` и `Retry-After`; при регулярном превышении применить временную блокировку |
| Авторизованное создание записи `POST /api/v1/booking-operations` | 10 запросов в минуту и burst 3 на `sub`; дополнительно 30 запросов в минуту на устройство | Вернуть `429` и `Retry-After`; не запускать SAGA. Повтор ранее принятой команды с тем же `Idempotency-Key` возвращает сохранённое состояние и не расходует командную квоту повторно |

Распределённый token bucket хранится в Redis Cluster. Лимиты применяются после
WAF и проверки формата запроса, а пользовательские квоты — после проверки
токена. Метрики `429`, заблокированные IP и аномалии по учётной записи поступают
в SIEM.

## Защита данных при передаче

- Использовать TLS 1.2/1.3 с современными cipher suites, HSTS и автоматической
  ротацией публичных сертификатов.
- Использовать mTLS и отдельную сервисную идентичность для внутренних вызовов;
  авторизовать сервис по scope, а не только по наличию сертификата.
- Не передавать access token, медицинские данные и идентификаторы пациента в URL;
  запретить их запись в access logs, traces и сообщения об ошибках.
- Передавать в push только нейтральный текст о готовности данных. Результат
  загружается приложением после повторной проверки access token.
- Валидировать размер, тип и схему входного JSON на Gateway; в сервисах применять
  параметризованные SQL-запросы, чтобы закрыть обнаруженную SQL injection.
- Ограничивать CORS только web-клиентами; для мобильного API не считать CORS
  механизмом аутентификации.
- Хранить ключи и сервисные секреты в secrets manager, регулярно ротировать их и
  не включать в конфигурацию приложения.
- Передавать `traceId` и `correlationId` без персональных данных; вести
  неизменяемый аудит чтения медицинской карты и изменения записи.
- Защитить token endpoint от credential stuffing с помощью rate limiting,
  обнаружения аномалий, MFA и отзыва refresh token при повторном
  использовании старого токена.
