# Надёжная поставка результатов анализов

## Выбор решения

Результаты доставляются через новый LIS Adapter и управляемый Event Broker. 
Адаптер каждые 30 секунд запрашивает из REST API LIS результаты,
изменённые после сохранённого watermark. Каждый запрос перекрывает предыдущий
интервал на пять минут: пропуск из-за рассинхронизации часов повторно попадёт в
выборку, а дедупликация исключит дубль.

Полученный результат и запись outbox сохраняются одной транзакцией в базе
адаптера. После подтверждённой публикации событие остаётся в broker семь дней.
Lab Results Service ведёт inbox с уникальным ключом `resultId + version`,
обновляет read model и только затем подтверждает offset. Таким образом доставка
происходит как at-least-once.

## Сравнение вариантов

| Вариант | Гарантированная доставка | Пиковая нагрузка | Эксплуатация | Оценка |
| --- | --- | --- | --- | --- |
| Прямой синхронный вызов LIS → Mobile API | Нет сохранённой очереди; таймаут приводит к потере или ручному повтору | LIS и Mobile API должны одновременно выдержать пик; нет backpressure | Мало компонентов, но сильная связанность и сложное восстановление | Не подходит |
| Чтение мобильным API из CRM | Зависит от старого LIS–CRM коннектора, который уже теряет и дублирует данные | Частый polling нагружает CRM; задержка достигает двух часов | Выглядит просто, но сохраняет неподдерживаемый коннектор и ручные перезапуски | Не подходит |
| LIS Adapter + event broker + Results Service | Durable inbox/outbox, at-least-once, дедупликация, retention и replay | Масштабируемая обработка; брокер сглаживает пики | Появляются новые компоненты, но за счёт управляемости, метрик и DLQ появляется управляемое восстановление | Выбрано |

Вместо RabbitMQ выбрана Kafka:
retention позволяет повторно построить read model и восстановить потребителя без
повторной выгрузки из LIS. Управляемая поставка снижает операционную сложность:
кластер, репликация и обновления не обслуживаются командой клиники.

## Поток данных

1. LIS фиксирует готовую или исправленную версию результата.
2. LIS Adapter запрашивает изменения через REST, используя watermark и
   перекрывающееся окно.
3. Адаптер проверяет контракт, записывает inbox и outbox одной транзакцией.
4. Outbox Publisher отправляет `LabResultPublished` в topic, используя
   `resultId` как partition key.
5. Lab Results Service проверяет `resultId + version`, обновляет read model и
   подтверждает offset.
6. Сервис публикует `LabResultAvailable`; сервис уведомлений отправляет пуш пользователю
   без диагноза и значений показателей.
7. Приложение после пуша или открытия экрана читает результат через Mobile API
   Gateway; Mobile BFF получает данные из read model и формирует ответ.
