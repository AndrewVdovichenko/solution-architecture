# Стратегия горизонтального масштабирования

## Выбор систем

Наиболее критичны Mobile API Gateway и сервис расписаний. Первый принимает и защищает весь
публичный трафик приложения, а второй находится в основном бизнес-сценарии и уже
испытывает блокировки PostgreSQL. Mobile BFF масштабируется независимо как
stateless backend, но не подменяет масштабирование этих двух узких мест.

## Стратегия

| ИТ-система | Реализация горизонтального масштабирования | Ограничение | Описание решения для него |
| --- | --- | --- | --- |
| Mobile API Gateway | Stateless-реплики минимум в трёх зонах доступности за L7 load balancer; автоматическое масштабирование по RPS, CPU и p95 latency; JWT проверяется локально; общие квоты хранятся в Redis Cluster; запросы распределяются между независимыми репликами Mobile BFF | Централизованное состояние rate limiting в Redis может стать узким местом или единой точкой отказа | Redis Cluster с шардированием по ключу пользователя/IP, replica failover и локальным краткоживущим token bucket на Gateway. При недоступности Redis авторизованные команды переходят в строгий локальный лимит, а публичный поиск — в ограниченный fail-open режим |
| Сервис расписаний | Stateless-реплики сервиса; команды направляются в PostgreSQL shard по `clinicId`, чтения — в read replicas; расписание кэшируется с событийной инвалидацией; каждый shard имеет primary и синхронную standby | Горизонтальное масштабирование не устраняет конкурентную запись двух пациентов в один слот и усложняет операции между клиниками | Уникальный индекс `(clinic_id, doctor_id, start_at)`, optimistic locking по `version`, атомарный `INSERT/UPDATE` и `Idempotency-Key`. Клиника является неизменяемым shard key; межклинический поиск агрегирует read models, а не выполняет распределённую транзакцию |

## Контрольные параметры

- Gateway масштабируется при средней загрузке CPU выше 60%, p95 выше 700 мс или
  превышении 70% расчётного RPS на реплику; минимум три реплики остаются всегда.
- Read replica сервиса расписаний выводится из балансировки при replication lag больше
  двух секунд; критичная проверка доступности слота всегда выполняется на primary.
- Нагрузочный тест состоит из разгона до 50_000 активных пользователей и
  отдельного всплеска конкурентных команд на один слот.
- Цель: `p99 < 1 с` для поиска и чтения расписания, отсутствие двойных броней и
  доступность пользовательского контура не ниже `99,95%`.
