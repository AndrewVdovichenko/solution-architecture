# Целевое решение

## Граница системы

На C4 Level 1 Mobile API Gateway и Mobile BFF показаны отдельными системами, 
потому что независимо развёртываются, масштабируются и имеют разные зоны
ответственности. Gateway защищает внешний периметр, выполняет OAuth, применяет
квоты и маршрутизирует запросы. BFF владеет мобильным контрактом, композицией
ответов и вызовами бизнес-сценариев.

Внутри Mobile BFF находятся Booking Orchestrator, адаптеры к существующим системам, брокер событий,
read models и средства наблюдаемости.

Веб-портал остаётся отдельной существующей системой. Врачи продолжают работать
через него, а мобильный backend создаёт параллельный канал только для
мобильного приложения.

## Принципы

- Мобильное приложение обращается только к API Gateway, а Gateway — только к BFF.
- Gateway не содержит бизнес-логику и не обращается к существующим системам.
- Веб-портал сохраняет существующие интеграции с расписанием, CRM, 1С, платежами и
  уведомлениями.
- Синхронные вызовы используются там, где пациенту нужен немедленный результат.
- Длительная обработка, результаты анализов и уведомления передаются асинхронно.
- Повторяемые команды идемпотентны.
- Все внутренние шаги используют `correlationId`, `traceId` и идентификатор
  бизнес-операции.

## Новые интеграции

| Интеграция | Стиль и паттерн | Протокол | Обоснование |
| --- | --- | --- | --- |
| Mobile App → Mobile API Gateway | Client-server, API Gateway | HTTPS/REST, OAuth 2.1/OIDC, Bearer JWT | Единый внешний endpoint для аутентификации, WAF, rate limiting, проверки обязательных заголовков и версионирования API |
| Mobile API Gateway → Mobile BFF | Gateway routing | mTLS/REST, исходный Bearer JWT | Gateway удаляет внешние служебные заголовки и передаёт проверенный запрос; BFF повторно проверяет токен и извлекает `patientId` |
| Mobile BFF → Расписание | Request-response, idempotent command | REST + `Idempotency-Key` | Чтение слотов и резерв требуют немедленного ответа; стабильный ключ исключают дубли |
| Mobile BFF → CRM | Request-response, API composition | REST | BFF получает профиль и медицинские данные авторизованного пациента, не раскрывая CRM наружу |
| Mobile BFF → LIS | Anti-Corruption Layer, request-response | REST adapter | Адаптер скрывает SOAP/FTP и нестабильность legacy-интеграции |
| LIS → Mobile BFF | Event-Driven Architecture, Outbox/Inbox, Idempotent Consumer | REST polling + durable broker внутри BFF | Версии результатов доставляются at-least-once, дедуплицируются и сохраняются в read model независимо от доступности приложения |
| Mobile BFF → 1С | Anti-Corruption Layer, Circuit Breaker, cache/read model | HTTP через адаптер 1С | Адаптер нормализует контракт и ограничивает нагрузку; локальное состояние позволяет не блокировать мобильный канал |
| Mobile BFF → Платёжный шлюз | Request-response, idempotent command | HTTPS/REST | Платёж использует стабильный `merchantPaymentId`; после timeout BFF сначала запрашивает статус и не допускает двойного списания |
| Mobile BFF → Уведомления | Publish/Subscribe, competing consumers, DLQ | Durable events | Уведомление не задерживает запись; retry и DLQ сохраняют неуспешные сообщения для восстановления |

## Внутренняя комбинация паттернов

Booking Orchestrator реализует оркестрируемую SAGA для проверки полиса,
резервирования записи к врачу в расписании, LIS и проведения платежа. Перед каждым внешним шагом
он сохраняет состояние, а при частичном отказе запускает компенсации.

После фиксации бизнес-операции transactional outbox публикует событие во
внутренний Event Broker. LIS, сервис проверки полисов и
сервис уведомлений используют inbox, дедупликацию, retry и DLQ. Таким образом
синхронный пользовательский путь остаётся коротким, а восстановление потребителей
не требует повторного действия пациента.
