# Реестр нефункциональных требований

Все целевые показатели относятся к MVP, если не указано иное. Для каждого показателя перед запуском должна быть настроена продуктовая телеметрия и внедрен метод повторяемой верификации.

| ID | Категория | Требование | Метрика | Целевое значение | Метод проверки | Источник | Статус / Ответственный |
|---|---|---|---|---|---|---|---|
| AVL-01 | Доступность | Чтение каталога должно оставаться доступным независимо от API партнеров | Доля успешных запросов от общего числа допустимых запросов (скользящее окно 30 дней) | ≥99.9% | Синтетические проверки + продуктовые SLI | Маркетинговый бриф: «менее двух секунд»; [Архитектурное видение, §4](../task2/architecture-vision.md) | MVP / CTO |
| AVL-02 | Доступность | Инициация платежа должна возвращать обрабатываемое состояние | Доля успешных попыток от общего числа валидных попыток (скользящее окно 30 дней) | ≥99.95% | Продуктовые SLI и тестирование отказов в песочнице провайдера | Опасения инвесторов по аптайму; [ADR-001](../task2/adr-001-architecture-style.md) | MVP / CTO |
| AVL-03 | Доступность | Уведомление должно оперативно доходить как минимум до одного провайдера | Доля событий, принятых каналом в течение ≤5 мин, от общего числа допустимых событий | ≥99.0% | Метрики приемки очередей/провайдеров | Описание MVP уведомлений | MVP / Operations |
| PRF-01 | Производительность | Первый результат каталога должен быть пригоден к использованию на целевом мобильном профиле | End-to-end P99 (задержка от начала до конца) | ≤2 с при 1.5 Мбит/с, 150 мс RTT, 1% потерь пакетов | Тест в браузере с пустым HTTP-кешем и прогретым Service Worker | Маркетинговый бриф, требования к пользовательскому опыту | MVP / Product engineering |
| PRF-02 | Производительность | Инициация платежа не должна заставлять покупателя ждать | API P99 до получения статусов `accepted`, `pending` или детерминированного отказа | ≤3 с | Нагрузочное тестирование с имитацией задержек провайдера | [Архитектурное видение, §4](../task2/architecture-vision.md) | MVP / Ответственный за платежи |
| PRF-03 | Производительность | Отправка уведомления в очередь не должна блокировать процесс оформления заказа | P99 задержка постановки в очередь | ≤1 с | Интеграционное/нагрузочное тестирование | [ADR-001](../task2/adr-001-architecture-style.md), решение об асинхронности | MVP / Ответственный за уведомления |
| CAP-01 | Масштабируемость | Каталог должен выдерживать пики рекламных кампаний с запасом мощности | Количество успешных запросов к каталогу в секунду | 500 RPS в течение 15 мин при загрузке CPU/DB ≤70% | Ступенчатое нагрузочное тестирование на данных объемом 5000 SKU | Маркетинговый бриф; допущения по нагрузке | MVP / Platform |
| CAP-02 | Масштабируемость | Платежный процесс должен справляться с наплывом трафика во время флеш-распродаж | Количество валидных инициаций платежей в секунду | 25 (устойчиво); 50 TPS в течение 5 мин | Нагрузочное тестирование с использованием заглушек провайдера; отсутствие дублирующих списаний | Требование маркетинга к флеш-распродажам | MVP / Ответственный за платежи |
| CAP-03 | Масштабируемость | Воркеры уведомлений должны успевать обрабатывать трафик запуска | Количество принятых сообщений в секунду и возраст старейшего сообщения в очереди | 100 сообщ/с; возраст очереди <5 мин | Нагрузочное тестирование с ограниченной пропускной способностью заглушек провайдера | Описание уведомлений | MVP / Ответственный за уведомления |
| REC-01 | Восстановление | Критическое состояние заказов/платежей должно быть восстановимо | RTO / RPO при сбое приложения или зоны доступности (AZ) | RTO ≤30 мин; RPO БД ≤5 мин | Ежеквартальные учения по восстановлению/отказу; сверка через вебхуки | Письмо CTO, стремление к RPO 0; бюджетные ограничения | MVP / CTO |
| REC-02 | Восстановление | Каталог должен восстанавливаться, сохраняя возможность чтения устаревших данных | RTO / RPO | RTO ≤60 мин; RPO ≤1 ч; устаревшие данные каталога ≤4 ч | Учения по восстановлению и тест отказа кеша/оригинального источника | Требование для мобильных устройств/оффлайн-режима | MVP / Ответственный за каталог |
| REC-03 | Восстановление | Надежная работа уведомлений должна сохраняться при сбое воркеров/провайдеров | RTO / RPO | RTO ≤4 ч; RPO ≤15 мин | Тест восстановления очереди и повторного воспроизведения | Решение по Outbox | MVP / Ответственный за уведомления |
| REC-04 | Целостность | Коллбэки провайдеров должны быть безопасны для повторной обработки | Количество побочных эффектов от дублирующихся событий | 0; 100% покрытие ключами идемпотентности | Контрактные тесты с дублирующимися/неупорядоченными вебхуками | [Архитектурное видение, §4](../task2/architecture-vision.md) | MVP / Ответственные за интеграции |
| SEC-01 | Безопасность | Данные должны быть зашифрованы при передаче и в хранилище | Покрытие эндпоинтов и хранилищ | TLS 1.2+; 100% управляемых хранилищ зашифрованы | Автоматизированное сканирование конфигураций | Юридическое письмо; намерения CN.SEC.03 | MVP / Ответственный за безопасность |
| SEC-02 | Безопасность | Секреты не должны попадать в код, образы, логи или телеметрию | Результаты сканирования секретов | 0 критических/высоких находок; поддержка ротации | CI-сканирование секретов и выборка логов | CN.SEC.03 | MVP / Platform |
| SEC-03 | Безопасность | Привилегированные действия и платежные операции должны быть аудируемы | Покрытие аудит-событий и их неизменяемость | 100% определенных действий; хранение 90 дней (до юр. проверки) | Тестирование безопасности и ежемесячная выборка | Юридическое письмо; риск лицензирования платежей | MVP / Ответственный за безопасность |
| SEC-04 | Конфиденциальность | Телеметрия не должна содержать необработанных персональных данных (PII), учетных данных или полных полезных нагрузок провайдеров | Количество найденных запрещенных полей | 0 | Тесты фильтров коллектора и еженедельная выборка | Юридическое письмо; [Вопрос Q-05](../task1/open-questions.md) | MVP / Ответственный за данные |
| MOB-01 | Эффективность мобильных устройств | Первоначальный опыт работы с каталогом должен ограничивать расход платных мобильных данных | Сжатая передача данных до получения первого результата | ≤500 КБ (исключая кешированную оболочку) | Тест в браузере с имитацией сетевого профиля | Маркетинговая аудитория: бюджетные Android-устройства/недорогие тарифы | MVP / Frontend |
| MOB-02 | Отказоустойчивость | Прерванные безопасные операции должны иметь возможность повтора | Дублирование заказов/списаний после переподключения | 0; идемпотентность на всех мутирующих эндпоинтах | Тесты прерывания сети / сквозные end-to-end тесты | Описание: нестабильное соединение 3G/LTE | MVP / Product engineering |
| OPS-01 | Наблюдаемость | Для каждого пути SLO должны существовать «четыре золотых сигнала» | Покрытие метриками/дашбордами | 100% путей каталога, платежей и уведомлений | Чек-лист дашбордов и пробный запуск алертов | CN.OBS.01/02; Требование | MVP / Platform |
| OPS-02 | Реагирование на инциденты | Быстрое выгорание error-budget должно приводить к оповещению ответственного | Покрытие скорости выгорания | Страницы при 14.4×/1 ч и 6×/6 ч; тикет при 1×/3 дн | Инъекция синтетических ошибочных событий | Метод burn-rate из SRE Workbook | MVP / On-call lead |
| OPS-03 | Развертывание | Изменения в продакшене должны быть автоматизированы и обратимы | Успешность деплоя/отката | 100% через CI/CD; откат ≤10 мин | Упражнение с имитацией сбоя канареечного релиза | CN.ADL.01/04/05/06 | MVP / Platform |
| OPS-04 | Состояние системы | Рантайм должен раскрывать состояние здоровья системы, не скрывая зависимости | Покрытие эндпоинтов | `/live`, `/ready`, `/health/dependencies`; 100% инстансов | Тесты деплоя и сбоев зависимостей | CN.FTL.02 | MVP / Platform |
| CLD-01 | Cloud Native | Приложение должно работать в виде неизменяемых контейнеров с явно указанными ресурсами | Покрытие образов/ресурсов | 100% компонентов runtime; лимиты при оркестрации | Политики образов и манифестов CI | Поведение MVP; отказ от использования Kubernetes | CN.RPL.01/03 | MVP |
| CLD-02 | Эластичность | Stateless-экземпляры приложения должны масштабироваться горизонтально | Количество одновременно работающих реплик | ≥2 в продакшене; состояние сессий вынесено вовне | Тест горизонтального масштабирования | CN.SEL.01 | MVP / Platform |
| CLD-03 | Слабая связанность | Модули/провайдеры должны взаимодействовать только через собственные API/порты | Нарушения границ | 0 прямых обращений к таблицам между модулями; 100% провайдеров за адаптерами | Архитектурные тесты и ревью кода | CN.LCP.03/05; ADR-001 | MVP / Architect |
| CLD-04 | Управляемы сервисы | Предпочтение отдается стандартным управляемым сервисам, если не доказано обратное | Записи об исключениях | ADR требуется для каждой БД/брокера | Архитектурное ревью | CN.MSV.01 | MVP / CTO |
| CST-01 | Стоимость | Регулярные технические расходы должны оставаться в рамках бюджета | Ежемесячный фиксированный счет за технические услуги | ≤$5,000/мес; алерт при достижении 80% прогноза | Дашборд бюджета и сверка счетов | Письмо CFO, пункт 1 | MVP / CFO + CTO |

## Статус контроля Cloud Native

| Контроль чек-листа | Статус |
|---|---|
| CN.RPL.03, CN.SEL.01, CN.FTL.02 | Внедрить декларации ресурсов (если поддерживаются рантаймом), обеспечить наличие двух реплик и стандартных эндпоинтов проверки состояния. |
| CN.LCP.03, CN.LCP.05 | Применить на границах модулей/провайдеров; требование независимого развертывания становится обязательным только после выделения в отдельные сервисы. |
| CN.MSV.01 | Принять; для команды из шести человек предпочтительны управляемые PostgreSQL и очереди. |
| CN.ADL.01/04/05/06 | Внедрить автоматизированное развертывание, конфигурацию как код (IaC), канареечные релизы и механизм отката. |
| CN.SEC.02/03/04 | Применяются внутренний реестр артефактов и управление секретами. |
| CN.OBS.01/02 | Внедрить метрики, логи и трассировку через OpenTelemetry. |
| CN.RPL.01 | Требование чек-листа по использованию Kubernetes вступает в конфликт с ADR-001; необходимо запросить отказ для MVP и показать эквивалент (контейнеризация, health checks, масштабирование и автоматизация). |
