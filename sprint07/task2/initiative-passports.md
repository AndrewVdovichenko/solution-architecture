# Задание 2. Паспорта инициатив

**Дата**: 10.09.2026

## Инициатива №1. Приоритизация подозрительных операций

### Раздел 2. Постановка

| Поле | Решение |
|---|---|
| Бизнес-действие | Изменить порядок ручного разбора операций, не отменяя обязательные правила ПОД/ФТ и решение сотрудника |
| Объект и единица решения | Операция в контексте клиента, контрагента и окон 1/7/30/90 дней |
| Момент | Сразу после совершения операции. На этапе пилота — суточный пакетная обработка в теневом режиме; в целевом режиме — асинхронно в рамках согласованного SLA. |
| Операция | Ранжирование и обнаружение аномалии |
| Модальность | Табличные данные, временные последовательности, краткое текстовое назначение платежа. |
| Выход модели | Некалиброванный скоринг, оценка выхода за пределы обучающей выборки, вклад признаков; модель не выносит вердикт о наличии «схематоза». |
| Бизнес-выход | Ранг в очереди, маршрут обработки, обоснование, сигналы срабатывания правил, показатели качества данных, версия решения и ссылка на исходную операцию. |
| Источник правильного ответа | Экспертная метка по гайдлайну; отдельно хранятся решение об эскалации, исход расследования и формальное подтверждение |
| Конвейер | Сбор событий → генерация признаков → работа модели → калибровка и установка порогов согласно емкости очереди → применение правил ПВК → формирование очереди → проверка сотрудником → сбор обратной связи. |
| Альтернативы | Классификатор отложен; использование только правил — baseline |

### Раздел 3. Оценка качества

| Поле | Решение |
|---|---|
| Бизнес-метрика | Число экспертно обоснованных эскалаций в 10 тыс. проверок; медианное время от совершения операции до ее проверки; трудозатраты на ручной разбор (человеко-минуты). |
| Положительный класс | Операции, классифицированные как «требующие углубленного расследования» согласно гайдлайну и результатам арбитража. Формально подтвержденные схемы учитываются отдельной метрикой с временным лагом. |
| Метрика под решение | Yield@K_policy по результатам слепой приёмочной разметки; полнота на вероятностной контрольной выборке (при условии достижения статистической мощности); PR-AUC — для диагностических целей. |
| Baseline | Текущие правила и приоритезация по сумме операции, заново измеренные с использованием той же методики слепой приёмочной разметки. 400 исторических эскалаций не используются в качестве эталона качества. |
| Проверочная выборка | Последний временной период, исключенный из процесса обучения; все размеченные элементы модельной очереди плюс стратифицированная выборка из полного потока с известной вероятностью включения. |
| Рабочая точка | K_total ≈ 10 000; после дедупликации K_policy = K_total − \| K_mandatory ∪ K_exploration \|. Если обязательные кейсы и контроль не помещаются, пилот блокируется |
| Показатели в точке | Точечная оценка относительного прироста Yield@K_policy ≥ 20% при нижней границе 95% доверительного интервала ≥ 10%; снижение медианного времени на ≥ 20%; полнота не ниже baseline более чем на 5 п.п. (при достижении расчетной мощности). |
| Цена ошибок | Пропуск: регуляторные меры, потери и позднее выявление. Ложный приоритет: расход 12 минут. Ложная приостановка: остановка честного платежа, жалоба и возможный переход клиента к конкуренту; модель сама приостановку не создаёт |
| Guardrails | Обязательные правила не обходятся; доля снятых приостановок не выше baseline 450/600 = 75%; жалобы не выше 120/мес. при нормировке на число приостановок; SLA не хуже baseline |

Порог 20% — минимальный операционный эффект, оправдывающий изменение процесса при неизменной очереди; до пилота владелец финмониторинга подтверждает его и цену ошибок. Статистический вывод строится по доверительным интервалам, а не по одной точечной оценке.

### Раздел 4. Готовность данных

| Поле | Решение |
|---|---|
| Решение | Поддержка приоритизации ручной проверки |
| Объект и гранулярность | Операция; контекст агрегируется без подмены единицы решения клиентом |
| Источник и владелец | Операционный контур и DWH — владелец данных банка; ПВК/исходы — финмониторинг; справочники — владельцы НСИ; доступ выдаёт Data Owner |
| Источник правильного ответа | Экспертная разметка, арбитраж, исход расследования, формальное подтверждение — отдельные поля и даты |
| Доступность признаков в проде | Использование только тех признаков, которые были доступны на момент совершения операции. Исключены результаты проверок, будущие агрегаты и иные формы утечки таргета. |
| Разметка | Использование гайдлайна с примерами; двойная независимая разметка не менее 20% пилотного набора; расчет коэффициента согласия Коэна (Cohen's kappa); арбитраж старшим экспертом. Целевой показатель κ ≥ 0,7. В случае низкого согласия — пересмотр гайдлайна (обучение supervised-модели запрещено). |
| Смещение отбора | Исторические данные размечены на основе существующих правил и сигналов; непроверенные операции не считаются «чистыми». Решение: использование постоянной случайной/стратифицированной контрольной выборки с известной вероятностью включения. |
| Репрезентативность | Стратификация по типам клиентов (ИП/ЮЛ), кодам ОКВЭД, стажу, суммам, каналам, регионам, типам контрагентов и сезонности; выделение редких, но высокорисковых кейсов. |
| Объём | 20–25 млн операций/мес.; около 35 тыс. флагов, 10 тыс. разборов, 400 эскалаций. Число формальных подтверждений недостаточно. Для `p=4%`, `e=1 п.п.`, расчетный объем составляет 1 476 независимых объектов.|
| Качество | Проверить пропуски, дубли, отмены, таймзоны, изменения ОКВЭД/справочников, неоднозначные контрагенты, текстовую кодировку. |
| Право использовать | Банковская тайна и персональные данные. Комплаенс, DPO и юристы подтверждают цель, основание, регион, договоры обработки, сроки хранения и состав полей. Архитектор фиксирует поток данных, но не является субъектом правового вердикта. |
| Вердикт | Выявлен **разрыв с планом закрытия**: допускается запуск сбора данных и разработка теневого прототипа ранжирования, однако запуск supervised-классификатора («схема/не схема») на данном этапе невозможен. |

**План устранения разрыва**: 2 недели на разработку гайдлайна и инструмента разметки; 2 недели на проведение предварительного изучения; далее 10–14 недель работы в теневом режиме. Решение о достаточности данных принимается на основе количества положительных примеров, показателя κ и ширины доверительного интервала.

### Раздел 5. Карточка эксперимента

| Поле | Решение |
|---|---|
| Где именно теряем | Из 35 000 выявленных флагов разбираются только 10 000; текущая приоритезация по сумме не оптимизирует полезность проверок и не охватывает 20–25 млн неразмеченных операций. |
| Гипотеза причины | Поведенческие, контрагентские и временные признаки дают более полезный порядок, чем сумма и набор пороговых правил |
| Конкурирующие объяснения | Улучшение вызвано простым воспроизведением правил; экспертная оценка непоследовательна; сигнал проявляется только ретроспективно; новый порядок просто перераспределяет известные сегменты. |
| Рычаг | Признаки, ранжирующая модель, функция потерь, квоты сегментов, калибровка и постобработка |
| Дешёвый различающий эксперимент | Теневой режим с последующей слепой разметкой; далее (после согласования) — рандомизированное сравнение (baseline vs challenger) только для параметра K_policy; использование контрольной выборки и абляция признаков. |
| Ожидаемый эффект | `Yield@K_policy` ≥20%, нижняя граница кластерного 95% доверительного интервала ≥10%; ≥20% снижения медианного времени разбора |
| Стоимость проверки | 10–14 недель до первичного go/no-go; валидация продолжается до рассчитанной мощности. Включены независимая/двойная разметка, аналитик/DS, теневой режим |
| Критерий остановки | Отсутствие статистически значимого улучшения; κ < 0,7 после корректировки гайдлайна; ухудшение показателей guardrails; недоступность признаков в режиме point-in-time; отсутствие правового допуска. |

## Инициатива №2. OCR кредитных документов

### Раздел 2. Постановка

| Поле | Решение |
|---|---|
| Бизнес-действие | Андеррайтер осуществляет верификацию данных в OCR-слое и корректирует выявленные расхождения вместо выполнения полного ручного ввода данных. |
| Объект и единица решения | Страница документа; пакет документов — единица оркестрации процесса. |
| Момент | Асинхронно после загрузки пакета, до начала аналитической работы андеррайтера. |
| Операция / модальность | Извлечение данных; типы входных данных: изображения и электронные документы. |
| Выход модели | Текстовые блоки, координаты разметки, язык и уровень достоверности. |
| Бизнес-выход | Версионированный машиночитаемый слой (OCR-слой), визуальная подсветка источника данных, статусы обработки: `accepted` (принято), `review_required` (требуется проверка), `failed` (ошибка). |
| Источник ответа | Верифицированная транскрипция контрольного набора данных и подтвержденные исправления, внесенные пользователями. |
| Конвейер | Антивирусная проверка и нормализация → классификация типа страницы → OCR-распознавание → применение схемы извлечения → проверка по порогам достоверности → ручная коррекция. |

### Раздел 3. Оценка качества

| Поле | Решение |
|---|---|
| Бизнес-метрика | Трудозатраты на техническую обработку пакета (человеко-минуты); доля страниц, не потребовавших ручной коррекции. |
| Положительный класс | Не применимо: задача направлена на извлечение данных, а не на бинарную классификацию. |
| Метрика | Character Error Rate / Word Error Rate; точность совпадения ключевых реквизитов; доля страниц, направленных на ручную проверку; задержка обработки пакета. |
| Baseline | Полный ручной ввод данных в рамках текущего среднего времени обработки пакета (1,5 часа); экономический эффект от внедрения OCR оценивается путем замера сокращения временных затрат. |
| Проверочная выборка | Стартовый бюджет на этапе исследования — 1 000 страниц с распределением по типам и качеству; итоговый объем каждого критического сегмента рассчитывается на основе целевой погрешности и 95% доверительного интервала; страницы внутри одного пакета рассматриваются как кластер. |
| Рабочая точка | Автоматическое принятие технического OCR-слоя допускается только при превышении порога достоверности и успешном прохождении всех проверок; в противном случае инициируется процесс ручной коррекции. |
| Критерии | Стартовые бизнес-пороги: CER ≤ 2% и точность ключевых реквизитов ≥ 98%; пороги утверждаются владельцем процесса до фиксации набора данных. Обеспечение прослеживаемости является обязательным контрактным требованием: результат без ссылки на источник отклоняется. Объем выборки для критических сегментов рассчитывается по верхней границе допустимой ошибки. |
| Цена ошибок | Ошибка в символе суммы или идентификатора является критической и обходится дороже, чем дополнительная ручная проверка; в связи с этим метрика точности ключевых реквизитов приоритетнее средней ошибки CER. |
| Guardrails | Сохранение связи каждого поля с исходной страницей и координатами; неизменность оригинала документа; запрет на автоматическое принятие документов низкого качества; запрет на автоматизацию принятия кредитных решений. |

### Раздел 4. Готовность данных

| Поле | Решение |
|---|---|
| Источник и владелец | Архив кредитных заявок; владелец данных — кредитный блок, технический ответственный — платформа управления документами. |
| Эталон | Результат ручной верификации и подтвержденные исправления; исходный документ документа остается единственным источником истины. |
| Доступность | Документ должен быть доступен до начала обработки заявки; метаданные качества рассчитываются синхронно с процессом обработки. |
| Разметка | Двойная независимая проверка ключевых реквизитов; процедура арбитража при выявлении расхождений; исправления, внесенные пользователем через интерфейс, не признаются эталоном без официального статуса подтверждения. |
| Смещение | Существует риск смещения выборки в сторону успешно обработанных файлов; в обучающий набор необходимо включить отклоненные документы, фотографии, сделанные на мобильные устройства и редкие форматы. |
| Репрезентативность | Учет разнообразия типов документов, используемых бухгалтерских систем, качества сканов и фотографий, разрешения, ориентации страниц, языка и количества страниц в пакете. |
| Объём | Точный объем данных на данный момент не определен; проведение инвентаризации на этапе исследования является обязательным. 1 000 страниц — это бюджет на первичную оценку, но не гарантия качества. |
| Качество | Необходим аудит на наличие поврежденных или зашифрованных PDF-файлов, дубликатов, пустых страниц, документов с разным DPI, рукописного текста и некорректных MIME-типов. |
| Право использовать | Документы содержат банковскую тайну и ПДн клиентов, их представителей и поручителей; решение о возможности использования внешних сервисов обработки принимается DPO, юридическим департаментом и комплаенсом. |
| Вердикт | **Запуск пилотного проекта возможен** после проведения инвентаризации данных и получения правового заключения о возможности использования контролируемого контура. |


### Раздел 5. Карточка эксперимента

| Поле | Решение |
|---|---|
| Где именно теряем | Фотографии низкого качества, сложные табличные структуры и ключевые числовые реквизиты. |
| Гипотеза | Применение предварительной обработки изображений и использование OCR с учетом топологии документа позволит снизить количество критических ошибок по сравнению с использованием универсальных решений. |
| Конкурирующие объяснения | Ошибки вызваны изначально низким качеством исходника; некорректной классификацией типа страницы; спецификой шрифтов или языка; повреждением структуры файла. |
| Рычаг | Качество предобработки, выбор OCR-кандидата, порог достоверности, логика маршрутизации в зависимости от типа документа. |
| Дешёвый эксперимент | Слепое сравнительное тестирование 2–3 кандидатов на фиксированном стратифицированном наборе данных с детализацией ошибок по этапам обработки. |
| Ожидаемый эффект | Снижение доли пакетов, требующих посимвольной ручной вычитки, не менее чем на 30% при условии соблюдения пороговых значений точности по ключевым полям. |
| Стоимость | Разметка не менее 1 000 страниц, вычислительные ресурсы для тестирования кандидатов и 2 недели на интеграцию прототипа. |
| Критерий остановки | Ни один из кандидатов не достигает целевого показателя точности по ключевым полям, либо экономический эффект от автоматизации не превышает затрат на ручную коррекцию. |


## Инициатива №18. Извлечение финансовых показателей

### Раздел 2. Постановка

| Поле | Решение |
|---|---|
| Бизнес-действие | Формирование верифицируемого черновика финансовой карточки кредитной заявки. |
| Объект и единица решения | Финансовый показатель за определенный период; пакет документов — единица оркестрации процесса. |
| Момент | Асинхронно после завершения этапов OCR/парсинга, до начала проведения андеррайтером финансовых расчетов. |
| Операция / модальность | Структурированное извлечение данных; типы входных данных: документы, таблицы, текстовые блоки. |
| Выход модели | Код показателя, значение, единица измерения, валюта, отчетный период, уровень достоверности и ссылка на источник. |
| Бизнес-выход | Финансовая карточка со статусами полей и списком выявленных противоречий; обязательное подтверждение карточки сотрудником перед использованием в анализе. |
| Источник ответа | Верифицированная финансовая карточка, заполненная андеррайтером и отдельно размеченный набор документов. |
| Конвейер | OCR/парсинг → классификация типа формы → извлечение данных → валидация по JSON Schema → нормализация → бухгалтерские сверки → верификация человеком. |

### Раздел 3. Оценка качества

| Поле | Решение |
|---|---|
| Бизнес-метрика | Трудозатраты на подготовку финансовой карточки (человеко-минуты); доля полей, не потребовавших ручной корректировки. |
| Положительный класс | Не применимо: оценивается точность извлечения каждого обязательного показателя. |
| Метрика | Точность совпадения значений на уровне полей после нормализации; precision/recall по факту наличия поля; точность определения периода и единицы измерения; доля полей с корректной ссылкой на источник. |
| Baseline | Полный ручной поиск и перенос данных в рамках текущего среднего времени обработки пакета (1,5 часа); замер временных затрат на данном этапе проводится до запуска пилота. |
| Проверочная выборка | Стартовый бюджет на этапе исследования — не менее 300 пакетов; итоговый объем выборки рассчитывается на основе допустимой погрешности для каждого критического показателя и типа формы. Обеспечивается стратификация по клиентам и временным периодам; страницы одного пакета не могут быть разделены между обучающей и тестовой выборками. |
| Рабочая точка | Автоматическое предложение значения для обязательного поля допускается только при прохождении валидации по схеме, наличии ссылки на источник и успешном прохождении бухгалтерских сверок; в противном случае статус поля устанавливается как `review_required`. |
| Критерии | Стартовые бизнес-пороги, утверждаемые владельцем процесса: точность совпадения суммы, периода и валюты ≥ 97%; полнота обязательных полей ≥ 98%. Наличие прослеживаемости  является обязательным. Для обеспечения статистической значимости при нулевой наблюдаемой ошибке используется «правило трех» для определения объема примеров каждого критического класса. |
| Цена ошибок | Ошибка в значении суммы при проведении кредитного анализа является критической и обходится дороже, чем дополнительная ручная проверка; пропуск поля является более безопасным сценарием, чем предоставление ложного значения. |
| Guardrails | Запрет на автоматическое принятие кредитных решений или скоринг; обеспечение доступности исходного документа в один клик; обязательное аудирование всех исправлений и фиксация авторства; запрет на скрытие выявленных противоречий. |

### Раздел 4. Готовность данных

| Поле | Решение |
|---|---|
| Источник и владелец | Пакеты документов и верифицированные финансовые карточки; владелец данных — кредитный блок. |
| Эталон | Значения полей, подтвержденные андеррайтером с обязательной ссылкой на источник в документе; исторические карточки без прослеживаемости рассматриваются только как слабый сигнал. |
| Доступность | Все входные данные должны быть доступны на момент принятия кредитного решения; любые внешние обогащения данных должны быть версионированы. |
| Разметка | Использование канонического словаря, включающего 20–30 приоритетных полей; проведение двойной независимой разметки контрольного набора; случаи неоднозначности должны фиксироваться отдельно и не допускается их разрешение методом «догадки». |
| Смещение | Существует риск доминирования стандартных форм, которые поддаются обработке легче; выборка должна быть стратифицирована по типу формы, используемой бухгалтерской системе, отрасли и качеству исходного OCR. |
| Репрезентативность | Учет балансов, отчетов о финансовых результатах, налоговых форм, банковских выписок, файлов Excel, документов в формате PDF, а также сканов и фотографий; новые версии форм рассматриваются как отдельный сегмент. |
| Объём | Точный объем не определен; проведение инвентаризации является обязательным для определения количества пакетов и полей. Стартовый бюджет — 300 пакетов; если рассчитанный объем для критически важного формата отсутствует, такие документы остаются в ручном маршруте обработки. |
| Качество | Контроль соответствия единиц измерения, валют, знаков, периодов, итоговых значений в таблицах, обработка объединенных ячеек и выявление противоречий в версиях одного и того же документа. |
| Право использовать | Действуют стандартные ограничения в отношении банковской тайны и персональных данных (ПДн); дополнительно требуется подтверждение правомерности хранения извлеченных производных данных и соблюдения сроков их удаления. |
| Вердикт | **Выявлен разрыв с планом закрытия:** приоритетной задачей является разработка канонической схемы и формирование эталона, привязанного к источнику, после чего возможен запуск пилотного проекта. |


### Раздел 5. Карточка эксперимента

| Поле | Решение |
|---|---|
| Где именно теряем | Использование синонимов для различных показателей, обработка сложных табличных структур, некорректное определение периодов и единиц измерения в неструктурированных формах. |
| Гипотеза | Применение извлечения с учетом топологии документа в фиксированную схему в сочетании с бухгалтерскими проверками позволит формировать безопасный черновик данных быстрее, чем при полном ручном вводе. |
| Конкурирующие объяснения | Основной источник ошибок — низкое качество OCR; неполнота разработанной схемы; наличие противоречий в самих документах; наличие ошибок в исторических карточках, используемых в качестве эталона. |
| Рычаг | Качество распознавания, точность поиска данных на странице, использование строго ограниченного формата вывода, полнота словаря, применение детерминированных проверок и установка порогов достоверности. |
| Дешёвый эксперимент | Использование эталонного набора из 300 пакетов; сравнительный анализ классических правил/табличных парсеров, локальной специализированной модели и локальной LLM; проведение абляционного исследования (отключение модулей OCR и валидации). |
| Ожидаемый эффект | Сокращение времени на подготовку финансовой карточки не менее чем на 30% при условии соблюдения установленных порогов качества по обязательным полям. |
| Стоимость | Разработка канонической схемы и проведение разметки, проведение сравнительных тестов 2–3 кандидатов, разработка прототипа интерфейса верификации. |
| Критерий остановки | Критические ошибки в значениях проходят этап автоматической проверки; неполная прослеживаемость данных; экономический эффект от сокращения времени ниже стоимости процесса проверки; отсутствие правового допуска. |
