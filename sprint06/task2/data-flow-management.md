# Управление потоками данных

Указанные значения SLA являются целевыми архитектурными допущениями для этапа MVP; финальные параметры должны быть подтверждены владельцами данных в процессе Discovery.

**Общие требования безопасности:** Все потоки данных используют протокол TLS, механизмы идентификации сервисов (Service Identity), принцип наименьших привилегий (Least Privilege), ведение аудита и шифрование данных при хранении (Encryption at Rest).

| Маршрут (Источник → Приёмник) | Данные и операции | Формат и периодичность | Режим передачи и SLA | Владелец | Контроль качества и мониторинг |
| :--- | :--- | :--- | :--- | :--- | :--- |

| **Customer MDM → CRM/Integration Layer** | Распространение Golden ID и обогащение профиля | Версионированные события + REST API | Асинхронно/API, p95 событий ≤ 5 мин, доступность API 99.9% | Customer Domain | Уникальность ID, проверка версий, контроль устаревания записей; мониторинг задержки и SLO. |

## Протоколы обработки сбоев

* Для исключения нарушения целостности при двойной записи, поставщик данных должен использовать паттерн Transactional Outbox или механизм CDC.
* Потребитель должен фиксировать обработанные `event_id`; повторная обработка одного и того же события не должна приводить к изменению состояния системы.
* Временные сбои обрабатываются механизмом повторных попыток с экспоненциальной задержкой. Критические ошибки направляются в очередь недоставленных сообщений DLQ с обязательным указанием причины и ответственного; повторная обработка выполняется только после устранения причины.
* Нарушение последовательности выявляется через контроль версий сущности; устаревшие события не должны перезаписывать актуальные данные.
* Выявленное расхождение при сверке данных блокирует публикацию сертифицированных витрин и отчетов, однако не должно влиять на работу операционных (OLTP) систем.
