# Что нужно сделать

В проекте предусмотрено четыре задания:

1. Проанализировать данные, сущности, критичность и типы хранилищ.
2. Определить мастер-системы и спроектировать потоки данных.
3. Спроектировать целевую архитектуру данных и аналитическую платформу.
4. Подготовить план миграции, cutover-план и технологическую дорожную карту.

Проектную работу нужно сдать в Git-репозитории. Создайте публичный репозиторий в GitHub и назовите его Solution-FinUnion-Data-Merger.

Решение каждого задания нужно загрузить в отдельную директорию: Task1, Task2, Task3 и Task4.

Если вы ещё не работали с Git-репозиторием, то воспользуйтесь инструкцией ниже. А если вы уверены в своих силах — пропускайте этот блок и переходите сразу к заданиям проектной работы.

## Задание 1. Анализ данных, сущностей и хранилищ

**Цель задания**: проанализировать данные двух организаций, выделить ключевые бизнес-сущности, описать связи между ними, классифицировать данные по критичности и предложить типы хранилищ.

### **Конкретные задачи**

**1. Выделите ключевые бизнес-сущности**

Определите не менее десяти ключевых сущностей данных, которые участвуют в объединении FinUnion и RetailBank.

Можно использовать стартовый список из описания кейса, но итоговый набор сущностей должен быть вашим архитектурным решением. Если вы добавляете или исключаете сущность, кратко объясните причину.

Для каждой сущности укажите:

- Название (например, Клиент)
- Описание — что отражает сущность
- Основные атрибуты (например, ФИО, ИНН, паспорт, телефон)
- Сущности, с которыми связана эта сущность
- Системы-источники, в которых сущность используется
- Критерий, по которому сущность попала в модель
- Проблемы качества — дубли, пропуски, разные форматы, устаревшие данные

**2. Постройте логическую модель данных**

Создайте ERD или логическую схему связей между ключевыми сущностями. Можно использовать PlantUML, Mermaid, Draw.io или Structurizr.

Минимально отразите связи между клиентами, счетами, договорами, продуктами, операциями и обращениями.

**3. Классифицируйте данные**

Создайте таблицу классификации данных, например, такую:

| Сущность | Категория данных | Критичность | Влияние на ИБ                                    | Средства защиты                       |
| -------- | ---------------- | ----------- | ------------------------------------------------ | ------------------------------------- |
| Клиент   | ПДн              | Высокая     | Утечка нарушает требования ИБ и законодательства | Шифрование, маскирование, RBAC, аудит |

**4. Предложите типы хранилищ**

Для разных групп данных предложите подходящий тип хранилища.

Нужно рассмотреть следующие типы:

- OLTP БД — для операционных данных: счетов, договоров, платежей
- MDM — для золотых записей клиентов и справочников
- DWH — для регламентированной отчётности и BI
- Data Lakehouse — для больших исторических и событийных данных
- Объектное хранилище — для документов, выгрузок, архивов
- Графовая БД — для связей клиентов и контрагентов, если они обоснованы
- Поисковый движок — для поиска по обращениям и клиентским данным, если он обоснован

**5. Используйте референсную модель BIAN**

Сопоставьте 8–10 ключевых сущностей с сервисными или близкими областями BIAN.

Не просто перечислите названия доменов, а объясните, как референсная модель помогает:

- унифицировать терминологию после слияния;
- определить границы владения данными;
- найти пересечения между системами FinUnion и RetailBank;
- подготовить целевые домены данных и data products.

Пример:

|Сущность|Возможная область BIAN|Зачем это нужно|
|---|---|---|
|Клиент|Party Data Management|Единый подход к клиентским данным|
|Счёт|Current Account|Унификация модели счёта|

Остальные сущности сопоставьте самостоятельно.

В результате структура Task1 должна быть такой:

Task1/

## Задание 2. Мастер-системы и потоки данных

**Цель задания:** определить мастер-системы для ключевых сущностей, описать владение данными, построить диаграмму потоков данных и опишите управление потоками данных.

### Конкретные задачи

**1. Определите мастер-системы**

Для каждой ключевой сущности определите мастер-систему в промежуточном и целевом состояниях.

Различайте:

- систему-источник, где данные сейчас хранятся физически;
- систему, где данные впервые появляются;
- мастер-систему с эталонными данными, откуда они должны распространяться в другие системы;
- MDM / Customer Hub — компонент для ведения золотой записи клиента или справочников, если он нужен.

Не назначайте MDM мастер-системой для всех сущностей автоматически. Например, для клиентских и справочных данных MDM годится, а счета, транзакции и финансовые операции должны оставаться в профильных банковских системах.

При определении мастер-систем используйте результаты маппинга BIAN из задания 1: покажите, какие BIAN-домены помогают определить границы владения клиентскими, счётными, платёжными, карточными и кредитными данными.

Пример:

|Сущность|Источники As-Is|Мастер-система на 3 месяца|Целевая мастер-система|Связь с BIAN|Обоснование|
|---|---|---|---|---|---|
|Клиент|FU CRM, RB CRM|MDM Customer Hub|MDM|Party Data Management|Нужна золотая запись клиента|

**2. Опишите правила владения данными**

На диаграмме отразите основные системы из ландшафта As-Is и целевые компоненты, которые нужны для промежуточного состояния.

- Create

Опишите минимум пять зависимостей или рисков на уровне данных.

## Задание 3. Целевая архитектура данных и аналитическая платформа

**Цель задания:** спроектировать целевую архитектуру данных объединённого банка (операционные хранилища, аналитическую платформу, пайплайны данных, каталог данных и модель управления данными).

### **Конкретные задачи**

**1. Спроектируйте целевую архитектуру данных**

Опишите архитектуру To-Be через 12 месяцев, в которой отразите выбранные вами компоненты для операционной и аналитической нагрузки.

Минимальный набор компонентов для рассмотрения:

- Operational Systems — для ядра банковской системы, CRM, карт, кредитов
- MDM — для золотых записей клиентов и справочников
- Integration Layer — для синхронного и асинхронного обмена
- Kafka или аналог — для событийных потоков
- DWH — для регламентированной отчётности
- Data Lakehouse — для больших исторических и событийных данных
- BI — для дашбордов и аналитики
- Airflow — для оркестрации batch-пайплайнов
- DataHub — каталог данных, lineage, владельцы

**2. Сравните архитектурные варианты**

Сравните минимум три подхода:

- DWH на PostgreSQL;
- Data Lakehouse;
- Data Mesh.

Для каждого подхода укажите:

- плюсы;
- минусы;
- когда подходит;
- применимость к кейсу FinUnion + RetailBank.

Выберите целевой подход и обоснуйте его.

Допустимый вариант — гибридная архитектура.

**3. Спроектируйте пайплайны данных**

Опишите минимум четыре пайплайна. Один из них должен быть простым пайплайном для DWH на PostgreSQL в промежуточном состоянии через три месяца.

Пример:

|Пайплайн|Источник|Приёмник|Тип|Инструменты|
|---|---|---|---|---|
|Клиентские данные|CRM, Core|MDM|ETL/ELT|Airflow, dbt|

Отдельно опишите 1–2 сценария обработки больших исторических или событийных данных. Например, обработку истории карточных операций, событий клиентских каналов или архивных выгрузок после слияния.

Для каждого сценария укажите следующие поля:

- Источник данных — откуда поступают данные
- Характер данных — исторические, событийные, архивные, полуструктурированные
- Целевое хранилище — DWH, Data Lakehouse, объектное хранилище
- Способ обработки — Batch, streaming, CDC, ETL/ELT
- Потребители — BI, риск-менеджмент, антифрод, регуляторная отчётность

**4. Спроектируйте аналитическую модель**

Выберите схему «звезда» или «снежинка» для одной аналитической области.

Пример формата для анализа транзакций:

|Тип таблицы|Пример|
|---|---|
|Fact|fact_transactions|
|Dimension|dim_customer|

Остальные факты и измерения определите самостоятельно.

Опишите, почему выбранная модель подходит для OLAP-нагрузки.

**5. Покажите доменные data-продукты**

Покажите, как элементы Data Mesh могут применяться в целевой архитектуре данных объединённого банка. Для этого предложите 3–5 доменных data-продуктов и свяжите их с BIAN или бизнес-доменами банка. Проектировать полноценный Data Mesh для всей организации не нужно — достаточно показать, какие доменные наборы данных могут быть оформлены как data-продукты, кто ими владеет и кто их использует.

Пример формата:

|Data product|Домен|Основные данные|Владелец|Потребители|
|---|---|---|---|---|
|Customer 360|Party / Customer Profile|Клиент, сегмент, контакты, согласия|Data Office / CRM-домен|CRM, BI, маркетинг, риск-менеджмент|

Остальные data-продукты предложите самостоятельно.

В результате структура директории Task3 должна быть такой:

Файл dwh-lakehouse.md должен содержать:

## Задание 4. План миграции, cutover и технологическую дорожную карту

**Цель задания:** разработать план перехода от ландшафта As-Is к целевой архитектуре из задания 3: определить этапы миграции, cutover-план, риски, фолбэки и технологическую дорожную карту.

### **Конкретные задачи**

**1. Опишите образ целевого результата**

На основе архитектуры из задания 3 опишите, что именно должно измениться за 12 месяцев:

- какие системы остаются;
- какие выводятся из эксплуатации;
- какие данные мигрируются;
- какие потоки переключаются;
- какие критерии подтверждают завершение перехода.

Таблица ниже задаёт формат описания:

|Вопрос|Что описать|
|---|---|
|Какие системы остаются|Например, Target Core, MDM, DWH, Lakehouse|

**2. Составьте инкрементальный план миграции**

Сделайте план минимум из шести этапов.

Пример:

|Этап|Содержание|Результат|
|---|---|---|
|Data discovery|Инвентаризация систем, таблиц, потоков, владельцев|Реестр данных|

**3. Подготовьте cutover-план**

Опишите план переключения для одного критичного домена, например «Клиентские данные» или «Управленческая отчётность».

Cutover-план должен включать шаги:

- Подготовка — проверка готовности систем, резервные копии
- Data freeze — какие данные временно нельзя менять
- Финальная выгрузка — какие данные выгружаются перед переключением
- Загрузка — куда и как загружаются данные
- Сверка — какие контрольные суммы и бизнес-проверки выполняются
- Переключение — как меняются маршруты потоков
- Фолбэк — как откатиться при ошибке
- Мониторинг — какие метрики отслеживаются после переключения

**4. Опишите риски миграции**

Создайте таблицу рисков, например, такую:

|Риск|Влияние|Вероятность|Митигация|
|---|---|---|---|
|Дубли клиентов|Ошибки в профиле и коммуникациях|Высокая|Правила сравнения, ручная верификация спорных случаев|

**5. Составьте технологическую дорожную карту**

Разделите технологии и подходы по зонам. Пример задаёт только формат, а наполнение выбирайте сами:

|Зона|Что включить|
|---|---|
|Adopt|MDM, Airflow, DWH, DataHub для каталога|

Объясните, почему технологии попали в каждую зону.

В результате директория Task4 должна включать:

```
Task4/
├── README.md
├── migration-target-state.md
├── migration-plan.md
├── cutover-plan.md
├── migration-risks.md
├── tech-roadmap.md
└── diagrams/
```
