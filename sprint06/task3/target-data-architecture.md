# Целевая архитектура данных через 12 месяцев

[Диаграмма](diagrams/target-data-architecture.puml) разделяет операционные системы,
доставку, хранение, обработку и потребление.

## Архитектурные компоненты

1.  **Операционные системы (Operational Systems):** Системы FU (CRM, Core, Cards, Loans) переходят в статус целевых систем учета (System of Record). Системы RB подключаются к контурам исключительно в рамках процессов миграции.
2.  **Управление мастер-данными (MDM):**
    *   **Customer MDM:** обеспечивает управление «золотыми записями» (Golden Record) и связями идентификаторов.
    *   **Product/Reference MDM:** управляет версиями продуктов, тарифов и общесистемными справочниками.
3.  **Интеграционный слой (Integration Layer):**
    *   **API Gateway / ESB:** обеспечивает выполнение командных запросов и синхронное взаимодействие.
    *   **Apache Kafka:** служит шиной для передачи событий.
    *   **CDC / Transactional Outbox:** гарантируют надежную и атомарную публикацию изменений из систем учета.
4.  **Слой хранения (Storage Layer):**
    *   **PostgreSQL DWH:** высокопроизводительное хранилище для формирования сертифицированной отчетности.
    *   **Data Lakehouse (Object Storage + Apache Iceberg):** масштабируемое хранилище для сырых данных, событий и аналитических таблиц.
    *   **Архивная зона:** выделенное хранилище с поддержкой политик жизненного цикла.
5.  **Слой обработки (Processing Layer):**
    *   **Apache Airflow:** оркестрация пакетных процессов.
    *   **dbt:** управление трансформациями данных на основе SQL.
    *   **Streaming Jobs:** нормализация и обогащение событий в реальном времени.
    *   **Trino (Presto):** высокопроизводительный SQL-движок для выполнения запросов к слою Lakehouse.
6.  **Управление данными (Governance):**
    *   **DataHub:** централизованный каталог метаданных (схемы, владельцы, статус качества данных).
    *   **Безопасность:** сквозное применение IAM/KMS, механизмов маскирования/токенизации и полного аудита действий.
7.  **Слой потребления (Serving Layer):**
    *   **BI-системы:** доступ к сертифицированным витринам данных.
    *   **Risk / Anti-fraud:** доступ к потокам событий и подготовленным признакам.
    *   **Регулятор:** доступ исключительно к утвержденным выгрузкам из DWH.

## Обеспечение надежности и целостности

- **Атомарность интеграции:** Связка записи в OLTP и публикации события реализуется через паттерны **Outbox** или **CDC**; прямая двойная запись (Dual Write) в систему и брокер строго запрещена.
- **Гарантии доставки:** Все события снабжены стабильным идентификатором и версией сущности; все потребители (Consumers) спроектированы как идемпотентные.
- **Контроль полноты:** Проверка происходит на всех этапах: `Source → Landing → Silver → DWH/Report`.
- **Неизменяемость данных:** Слой сырых данных является неизменяемым; исправление логики трансформации всегда приводит к созданию новой версии результата, а не к затиранию старой.
- **Управление доступностью:** Параметры RPO/RTO определяются на основе анализа влияния на бизнес; любые показатели, не подтвержденные сверкой, помечаются как «допущения».
- **Защита персональных данных:** Персональные данные токенизируются до попадания в широкие аналитические зоны; доступ к ним строго ограничен бизнес-целями.

## Стратегия вывода устаревших систем

Процесс вывода систем RB (CRM, Core, Cards, Loans) из эксплуатации осуществляется поэтапно для каждого домена. Переход включает следующие стадии:
1.  **Historical Load:** полная загрузка исторических данных.
2.  **CDC Catch-up:** синхронизация изменений, накопленных за период загрузки.
3.  **Shadow Read / Parallel Run:** параллельная работа систем для верификации результатов.
4.  **Сверка и Cutover:** финальная сверка данных и переключение управления на целевую систему.
5.  **Стабилизация:** период мониторинга после переключения.

После достижения точки невозврата система переводится в режим только чтение, архивируется и выводится из эксплуатации при выполнении всех критериев выхода.
