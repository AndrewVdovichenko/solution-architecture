# Сравнительный анализ архитектурных подходов

В данном разделе представлено обоснование выбора целевой архитектуры данных на основе сравнения трех концепций.

| Подход | Преимущества | Недостатки | Рекомендованное применение | Применимость к FinUnion |
| :--- | :--- | :--- | :--- | :--- |
| **Классический DWH (на базе PostgreSQL)** | Быстрый запуск MVP; использование проверенного SQL/ACID; предсказуемая и строгая модель отчетности. | Ограниченное горизонтальное масштабирование при хранении сырой истории и потоковых данных; высокая стоимость пересчета больших объемов. | Умеренные объемы данных; жесткая схема; приоритет BI-отчетности. | **Этап «3 месяца»:** формирование единых фактов и сертифицированных витрин; не используется для хранения всей истории событий. |
| **Data Lakehouse** | Высокая масштабируемость на базе Object Storage; поддержка форматов таблиц поверх файлов; обработка batch/streaming; поддержка эволюции схем. | Повышенная сложность эксплуатации, управления и настройки производительности; не подходит для OLTP-нагрузок. | Хранение больших исторических массивов; событийных моделей; задач ML/антифрода и сценариев повторной обработки данных. | **Этап «12 месяцев»:** хранение истории транзакций по картам/каналам, архивов и решение задач исследовательской аналитики. |
| **Data Mesh** | Децентрализация ответственности (доменные владельцы); создание готовых Data Products; контроль качества данных максимально близок к источнику. | Требует высокой зрелости команд и наличия развитой платформы; риск дублирования данных и расхождения семантики. | Организации с множеством автономных и зрелых бизнес-доменов. | **Принципы:** внедрение подходов *ownership* и *product thinking*; отказ от построения полноценной распределенной платформы в пользу централизованных сервисов. |

## Архитектурное решение (Target Architecture)

Для проекта FinUnion принята **гибридная архитектура**, сочетающая преимущества различных подходов:

1. **PostgreSQL DWH:** используется как слой сертифицированных отчетных данных для обеспечения быстрого согласования ключевых показателей в рамках MVP.
2. **Data Lakehouse (на базе Object Storage):** выступает в роли масштабируемого хранилища для всей истории изменений, сырых событий и исследовательских задач.
3. **Единая платформа:** предоставляет общую инфраструктуру для управления метаданными, качеством и безопасностью.
4. **Доменные Data Products:** разработка 3–5 ключевых продуктовых наборов данных (например, Customer 360, Transactional Fact).

**Вывод:** Данный подход позволяет получить измеримый результат через 3 месяца, избегая преждевременного внедрения сложного Data Mesh, но при этом закладывает фундамент для перехода к полномасштабной архитектуре через год.

## Анализ отклоненных вариантов

- **Исключительно DWH:** несет в себе риск смешивания сертифицированных и сырых данных, а также приведет к критическому росту стоимости хранения событийного лога.
- **Исключительно Lakehouse:** повышает риски срыва сроков MVP и создает сложности с обеспечением регуляторной воспроизводимости отчетности на ранних этапах.
- **Полноценный Data Mesh:** реализация данной концепции в течение года невозможна, так как потребуется масштабная организационная трансформация, превышающая текущий уровень зрелости процессов (отсутствие каталога, закрепленных владельцев и единой модели данных).
