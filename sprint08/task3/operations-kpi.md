# Панель KPI эксплуатации целевой архитектуры

## Регламент измерения и методология

* **Временные интервалы (Windows):**
    * **Доступность (Availability):** рассчитывается за календарный год с контролем через скользящие окна 30 дней.
    * **Задержки (Latency):** мониторинг по минутным интервалам и суточным агрегатам.
    * **Пропускная способность (Throughput):** замер по пиковым окнам продолжительностью не менее 60 минут.
* **Определение доступности (Availability Definition):**
    * В расчет включаются только технически валидные запросы и результаты синтетических проб.
    * Ошибки со стороны клиента (валидация, авторизация) исключаются.
    * Ошибки сервера (`5xx`), таймауты шлюза (Gateway Timeout), а также ошибки `429 Too Many Requests` (вызванные исчерпанием мощностей) и неспособность системы принять валидный запрос классифицируются как **Down (ошибка)**.
* **Гарантия доставки (Delivery Guarantees):**
    * Событие считается принятым только после получения подтверждения записи (**durable acknowledgement**).
    * **Потеря (Loss):** событие, признанное принятым, но отсутствующее во всех целевых состояниях, при отсутствии записей в Retry-очередях или DLQ (Dead Letter Queue) по истечении установленного SLA.
    * Дублирование сообщений допустимо на уровне транспорта, если оно не влечет за собой повторного выполнения бизнес-логики (обеспечивается через идемпотентность).
* **Синхронизация времени:**
    * Все узлы системы должны быть синхронизированы через корпоративный NTP; максимально допустимое расхождение (clock skew) ≤ 100 мс.
    * **DWH Lag** рассчитывается как разница между моментом фиксации транзакции в источнике (`source_committed_at`) и моментом записи в DWH (`dwh_ingested_at`).
* **Приоритетность метрик:**
    * Перцентили (p95/p99) используются для оценки качества массовых запросов.
    * **Метрики нулевой толерантности (Zero-Tolerance Metrics)** — потеря платежных ответов, нарушение логики Saga/EDI, утечка PAN/ПДн — контролируются через абсолютные счетчики и процедуры сверки (reconciliation), а не через перцентили.

## Матрица ключевых показателей

| Технический показатель (SLI) | Целевое значение (SLO) | Метод замера и инструментарий | Бизнес-ценность (Зачем это нужно) |
| --- | --- | --- | --- |
| **Доступность транзакционного ядра** | ≥ 99,95%; Error Budget ≤ 4 ч 23 мин/год | Prometheus/Grafana + Blackbox Exporter (синтетические сценарии). `SLI = valid_requests / total_requests`. | Минимизация простоев при оформлении заказов и исключение потерь выручки. |
| **Пиковая производительность** | ≥ 200 заказов/с (в течение 60 мин); Tech errors < 0,1% | Нагрузочное тестирование (k6/Gatling). Метрики Ingress и Orders: RPS, p95/p99 latency, CPU/DB saturation. | Подтверждение масштабируемости системы при десятикратном росте нагрузки. |
| **Пропускная способность логистики** | ≥ 500 000 отправлений/сутки; Backlog → 0 к концу дня | Счётчики Kafka/DWH (`OrderAccepted`, `ShipmentCreated`, `DeliveryCompleted`). Сверка по `shipment_id`. | Гарантия того, что рост входящего потока не создает скрытых задержек в обработке. |
| **Устойчивость IoT** | 3 000 событий/с; 6 000 событий/с (всплеск до 5 минут); Loss = 0; p99 ack ≤ 500 мс | Prometheus + Kafka JMX Exporter. Проверка `sequence_id` по `device_id`, producer ack, consumer lag. Chaos/Soak testing. | Защита основного контура от влияния телематики и обеспечение контроля транспорта. |
| **Задержка данных в DWH** | Ключевой статус ≤ 5 с; `count(lag > 5s) = 0` за сутки | OpenTelemetry (correlation ID), Debezium/Kafka Connect metrics. Сверка по LSN и бизнес-ключам. | Обеспечение оперативной аналитики холдинга в режиме, близком к реальному времени. |
| **Надежность платежных вебхуков** | Потеря ответов банка = 0; 100% фиксация до HTTP ACK; Backlog = 0 | Ingress journal, `provider_event_id`, Outbox/DLQ, ежедневная сверка с реестром банка. | Исключение потери оплат, двойных списаний и необходимости ручного поиска платежей. |
| **Целостность бизнес-процессов (Saga/EDI)** | Нарушение логики переходов = 0; 100% документов имеют финальный статус | Аудит по `correlation_id`. Контроль `invalid_transitions`. | Предотвращение оплаты товаров без подтвержденной отгрузки и потери документов. |
| **Здоровье событийной платформы** | Loss = 0; `UnderReplicatedPartitions = 0`; Critical DLQ ≤ 15 мин | Kafka JMX, Burrow, Schema Registry, DLQ Dashboard. Алертинг по ISR, диск, lag и Schema Rejects. | Раннее обнаружение проблем до их влияния на финансовые и логистические процессы. |
| **Восстановление (DR/BCP)** | RPO = 0; RTO ≤ 15 мин (для одной зоны/узла) | Регулярные DR-drills (failover/restore). Сверка offset/LSN и бизнес-ключей после восстановления. | Гарантия непрерывности бизнеса и достижимости показателя доступности 99,95%. |
| **Комплаенс и изоляция данных** | PAN в контуре = 0; ПДн в DWH = 0; Несанкционированный доступ = 0 | DLP-сканирование топиков и логов; SIEM-аудит Profile Service и KMS; автоматические Access Tests в CI/CD. | Минимизация регуляторных (ФЗ-152/PCI DSS), репутационных и финансовых рисков. |

## Регламент эксплуатации и реагирования

1.  **Распределение ответственности:**
    * **Service Owners:** реагируют на деградацию SLO и превышение Error Budget.
    * **NOC:** мониторинг инфраструктурных сигналов и доступности сервисов.
    * **Data Team:** контроль контура CDC, Kafka и наполнения DWH.
    * **Payment Team:** проведение ежедневных сверок с банковскими реестрами.
    * **Security Team:** мониторинг DLP, SIEM и контроль целостности контуров ПДн.
2.  **Управление инцидентами:**
    * Нарушение любого показателя из категории **«Нулевая толерантность»** автоматически инициирует инцидент уровня **Critical**.
    * Нарушение критического показателя блокирует возможность проведения следующего этапа миграции.
    * При повторном нарушении показателей Latency или Availability в двух последовательных окнах запускается процедура ограничения нагрузки (Throttling) или отката (Rollback) последнего изменения.
3.  **Управление порогами:**
    * Бизнес-пороги (99,95% доступности, 500к отправлений, 3к RPS, DWH ≤ 5с, нулевая потеря оплат) являются константами. Любое изменение данных показателей требует обязательного согласования с **Архитектурным штабом**.
