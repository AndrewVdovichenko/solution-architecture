# Отработка возражений по целевой архитектуре Fast Cargo

## 1. Технический риск: влияние внедрения CDC на стабильность Legacy-системы
## Возражение Техлида
*«Внедрение промежуточных механизмов для извлечения данных (CDC) может создать критическую нагрузку на монолит и потребовать вмешательства в его исходный код, что ставит под угрозу текущие процессы отгрузок».*

### Позиция архитектора
Решение базируется на том, что мы не вносим изменения в исходный код монолита и не меняем существующие транзакции.

Механизм Debezium работает на уровне протокола логической репликации PostgreSQL (WAL). Чтение изменений происходит из логов транзакций, а не путем выполнения `SELECT`-запросов к операционным таблицам, что исключает блокировки бизнес-процессов. Для минимизации рисков начальная загрузка данных выполняется не из «живой» базы, а из физического бэкапа, развернутого в изолированном контуре.

Интеграция с Kafka является асинхронной: даже в случае сбоя в аналитическом контуре (DWH) или Kafka, монолит продолжает работу в штатном режиме, так как потоки данных полностью разделены.

### Меры по минимизации рисков
* **Валидация нагрузки:** Перед промышленной эксплуатацией проводится нагрузочное тестирование на базе текущего baseline. Допустимое отклонение показателей `p95 latency` и `error rate` монолита — не более 5%. Целевая доступность ядра ≥ 99,95%.
* **Контроль ресурсов СУБД:** Устанавливаются жесткие лимиты на объем хранящихся логов репликации (`max_slot_wal_keep_size`). Внедряется многоуровневый мониторинг:
    * При достижении 40% лимита WAL — предупреждение;
    * При достижении 70% или дефиците дискового пространства < 30% — аварийная остановка коннектора для защиты основной БД.
* **Контроль целостности:** Сверка данных осуществляется по LSN (Log Sequence Number), количеству записей и контрольным суммам. Допустимый уровень потерь — 0.

### План отката
В случае обнаружения аномалий процедура отката не затрагивает операционную деятельность: останавливается sink-коннектор, закрывается доступ к новой витрине DWH и удаляется replication slot. Монолит при этом остается единственным источником истины и продолжает работу без изменений.

## 2. Риск комплаенса: защита персональных данных (ФЗ-152) в CRM

### Возражение ИБ холдинга
*«Предоставление доступа CRM к данным из общего монолита нарушает требования ФЗ-152, так как ПДн находятся в едином контуре с операционными данными».*

### Позиция архитектора
Целевая архитектура предполагает полную **сегментацию данных**. Прямого доступа CRM к базе данных монолита не будет ни на переходном, ни на целевом этапе.

Все персональные данные (паспорт, телефон, email) будут вынесены в изолированный **Profile/PII Service**. Этот сервис обладает собственной выделенной базой данных, отдельным сетевым сегментом и строго контролируемыми сервисными учетными записями. CRM взаимодействует с этим сервисом исключительно через API Gateway, используя протоколы mTLS и OAuth2, получая только те атрибуты, которые необходимы для выполнения конкретной бизнес-задачи.

Для аналитического контура (DWH) применяется стратегия **обезличивания**: устойчивые идентификаторы удаляются или агрегируются таким образом, чтобы исключить возможность повторной идентификации субъекта.

### Меры по минимизации рисков
* **Организационные меры:** Проведение классификации ПДн, моделирования угроз и определения правовых оснований обработки данных.
* **Технические меры:** Применение ролевой модели доступа (RBAC/ABAC), маскирования полей на уровне БД (field-level masking), использования KMS/HSM для управления ключами и полного аудита всех операций чтения/экспорта данных.
* **Независимая проверка:** Перед запуском CRM обязательны проведение оценки воздействия на защиту данных (DPIA), тестов на проникновение и проверка невозможности повторной идентификации данных в DWH.

### План отката
Доступ CRM предоставляется поэтапно по группам пользователей и правам доступа. В случае нарушения политики безопасности API Gateway мгновенно отзывает токены, изолируя доступ, не влияя на операционные процессы заказов.

## 3. Риск производительности: высокочастотный IoT-трафик

### Возражение производственного департамента
*«Поток телематики в 3 000 RPS создаст избыточную нагрузку на инфраструктуру и СУБД, что может привести к деградации системы».*

### Позиция архитектора
Архитектура предусматривает **полную изоляцию трафика телематики** от основного бизнес-контура. Данные от датчиков не проходят через шлюз BFF, монолит или его базу данных PostgreSQL.

Для приема данных поднимается выделенный контур **Telemetry Ingest** (MQTT/HTTPS). После первичной валидации события попадают в Kafka, где обеспечивается механизм обратного давления. Это гарантирует, что даже при пиковых нагрузках система будет масштабироваться горизонтально, не создавая рисков для других сервисов. Хранение координат будет реализовано в специализированных Time-Series или Object Storage.

### Меры по минимизации рисков
* **Нагрузочное тестирование:** Проверка способности системы обрабатывать 3 000 RPS в постоянном режиме и кратные всплески (x2) с соблюдением целевых показателей задержки0.
* **Отказоустойчивость:** Развертывание кластера Kafka с фактором репликации `RF=3` в нескольких зонах доступности и настройка `acks=all` для обеспечения гарантии доставки.
* **Управление квотами:** Внедрение квот на устройства, валидация схем данных на входе и использование механизмов автоматического масштабирования.

### План отката
Внедрение начинается с **канареечного релиза** (подключение ограниченной группы транспортных средств). При обнаружении роста задержек или нехватки ресурсов новые подключения блокируются, а устройства переходят в режим работы с локальным буфером или сниженной частотой передачи. Монолит и OLTP-система при этом остаются полностью защищенными.

## Пакет доказательств для защиты проекта

| Объект возражения | Необходимый артефакт | Критерий успеха | Ответственные |
| :--- | :--- | :--- | :--- |
| **Стабильность Legacy** | Отчет о нагрузочном тестировании, дашборды мониторинга WAL/Slot, Runbook отката. | $\Delta$ p95/error rate ≤ 5%, свободное место на диске ≥ 30%, 7 дней работы в Shadow-режиме без потерь. | Техлид, DBA, Операционный блок |
| **Комплаенс (ФЗ-152)** | Модель угроз, Data-flow диаграмма, отчет DPIA/Pentest. | Отсутствие прямого доступа к OLTP; отсутствие ПДн в DWH; закрытие критических замечаний ИБ. | DPO, ИБ, Юридическая служба |
| **Нагрузка IoT** | Capacity Model, отчет о тестировании, FinOps/TCO расчет. | Обработка 3 000 RPS + всплески без потерь; восстановление лага после пиковых значений; устойчивость при отказе узла. | Инфраструктура, Эксплуатация |
